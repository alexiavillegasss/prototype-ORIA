===============================================================================
                    ORIA - ARCHITECTURE DES DOSSIERS & PROJET
===============================================================================

Ce document explique l'organisation des fichiers et dossiers du projet ORIA.
L'architecture d'ORIA est inspirée des meilleures pratiques de la "Clean Architecture"
et du "Domain-Driven Design" (DDD). Elle garantit la séparation des responsabilités,
la maintenabilité du code et une extensibilité simplifiée.

2. LES 3 GRANDS PRINCIPES DE CETTE ARCHITECTURE
-------------------------------------------------------------------------------

A. SÉPARATION DES RESPONSABILITÉS (Separation of Concerns)
   Chaque dossier a une mission unique et hermétique :
   - Le dossier "ai" ne sait pas comment fonctionne le calcul du score.
   - Le dossier "application" (scoring, règles) contient la logique métier
     pure. Il est 100% indépendant des frameworks : il ne sait pas qu'il existe
     une base de données SQLite ou un serveur FastAPI. Si vous changez de base
     de données ou de serveur web demain, ce code n'a pas à être modifié.
   - Le dossier "infrastructure" gère les détails techniques de bas niveau :
     l'écriture des fichiers, les requêtes réseau et les requêtes SQL.

B. ARCHITECTURE DÉCLARATIVE & GUIDÉE PAR LA DONNÉE (Data-Driven)
   Toute la configuration et la logique d'aiguillage sont en dehors du code
   Python, centralisées dans le répertoire "/config".
   - Si un numéro de téléphone change dans le Var, vous modifiez le fichier JSON.
   - Si les règles du DAC ou du CRT évoluent (ex: GIR 3 au lieu de GIR 2), vous
     modifiez le fichier JSON.
   - Un utilisateur non-développeur peut ajuster le comportement d'ORIA
     sans toucher à une ligne de code Python.

C. SUITE DE TESTS CLINIQUES ISOLÉE
   Le dossier "/tests_simulation" est une force majeure du projet. Il regroupe
   24 cas patients réels d'école. Il fait office de filet de sécurité : à chaque
   mise à jour du code, vous pouvez lancer ces scripts pour vous assurer qu'aucun
   diagnostic ni aiguillage n'a été altéré.

-------------------------------------------------------------------------------
3. LE FLUX D'EXÉCUTION D'UNE REQUÊTE DANS CETTE STRUCTURE
-------------------------------------------------------------------------------

Quand un récit patient arrive sur l'application :

1. L'API (main.py) reçoit le texte et l'envoie à l'extracteur.
2. L'Extracteur (ai/extractor.py) appelle le client Ollama (infrastructure/llm_client.py)
   avec une température de 0.0 (déterministe) pour obtenir un JSON propre.
3. L'Extracteur traduit ce JSON brut selon le moule officiel (config/schemas/schema_definition.json).
4. Le Scoring (application/scoring_engine.py) calcule le score COMID à partir
   des règles définies dans config/rules/COMID.json.
5. L'Orientation (application/orientation_engine.py) évalue les règles logiques
   définies dans config/rules/orientation_rules.json, et filtre/fusionne
   les structures en éliminant les doublons.
6. Le Territoire (application/territory_manager.py) injecte les coordonnées physiques
   à partir du référentiel config/referentials/referentiel_territoire.json.
7. La Base de Données (infrastructure/database.py) enregistre le tout.
8. L'API (main.py) renvoie le résultat complet au format JSON.
